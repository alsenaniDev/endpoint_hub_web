TWK Endpoints Hub — User Guide

A complete, step-by-step guide for anyone using the TWK Endpoints Hub. No technical background required — just follow the sections in order.

API Discovery Live Testing Change Tracking Governance Real-time Collaboration

1.What is TWK Endpoints Hub?

TWK Endpoints Hub is a central portal for discovering, documenting, testing, and governing APIs across your organization.

Instead of hunting through scattered Swagger pages, spreadsheets, and Postman collections, everyone works from one place where they can:

  • See every API endpoint across all your teams, systems, and environments.
  • Automatically import endpoints from Swagger/OpenAPI documents — and keep them up to date.
  • Track what changed — new, modified, or removed endpoints — over time.
  • Test endpoints live with saved credentials, right from the browser.
  • Share and favorite endpoints so teammates find what they need fast.
  • Enforce API standards ("governance") and measure how compliant each API is.
  • Get real-time notifications when something is shared with you or a sync completes.

The product has two parts that work together:

Part What it is Who touches it
Web App (Angular) The website you log into and click around in. Everyone
API (.NET) The engine behind the scenes that stores data, syncs Swagger, runs requests, and sends notifications. Admins / IT during setup

You only need the Web App to use everything in this guide.

2.Key Concepts (Read This First)

The system is organized as a simple hierarchy. Understanding it makes everything else click:

Team
 └── System            (an application or service, e.g. "Payments Service")
      └── Environment  (e.g. Dev, Test, Staging, Production)
           └── Swagger Source   (a versioned OpenAPI document, e.g. "v1", "v2")
                └── Endpoints    (individual API operations, e.g. GET /orders)
  • Team — a group of people (e.g. "Checkout Team"). Owns systems.
  • System — one application or microservice.
  • Environment — a deployment of that system: Local, Development, Test, Staging, or Production. Each has a Base URL (where requests go) and optionally a Swagger URL (where the API description lives).
  • Swagger Source — a single OpenAPI/Swagger document. An environment can have several (for example, one per API version).
  • Endpoint — one API operation, such as GET /api/orders/{id}. These are imported automatically from Swagger — you rarely create them by hand.
  • Auth Profile — a saved set of credentials (token, API key, username/password, etc.) used to call endpoints.

Rule of thumb: You create Teams → Systems → Environments, point each environment at a Swagger URL, run a Sync, and the endpoints appear on their own.

3.Getting Started

3.1 Signing In

  1. Open the web app in your browser (ask your admin for the URL, e.g. http://localhost:4200 in development).
  2. On the Login screen, enter your email/username and password.
  3. Click Sign in. Choose an organization you belong to, then continue to a workspace available under your verified membership and permissions.

3.2 Creating an Account (Self-Registration)

If self-registration is enabled:

  1. On the login screen, switch to Register.
  2. Fill in the required Username and Email, and choose a Password (at least 6 characters). Full name is optional; password confirmation is checked before submission.
  3. Click Create account. If registration succeeds, you are signed in and can choose an organization.

If you can't register, an administrator needs to create your account (see Users & Roles).

3.3 First-Time Checklist for a New Workspace

If you're setting the portal up from scratch, do this in order:

  1. Create a Team → Section 6
  2. Create a System under that team → Section 7
  3. Create an Environment and add its Swagger URL → Section 8
  4. Run a Swagger Sync to import endpoints → Section 9
  5. Create an Auth Profile so you can test endpoints → Section 11
  6. Browse the Endpoints and try running one → Section 10

4.The Interface at a Glance

The application and Workbench share the Endpoints Hub color system: a neutral canvas (#F4F6F8), white surfaces, dark ink (#17202A), blue actions (#2563EB), and dark code surfaces (#101820). Green indicates success, amber indicates warnings, and red indicates danger. Small secondary labels and success messages use slightly darker variants for readable contrast. The theme toggle retains the existing dark palette, with its existing blue used for the product accent; a separate Figma dark-mode reference is still required for exact dark-theme matching.

Workbench Settings — Members and access: open /workbench/settings/members to inspect the active organization's existing member directory. Search by name, username or organization role, filter by directory role, and select a member to inspect membership details. The Roles tab shows roles used by valid members, not the global role catalogue. The access-context panel describes your own live membership, not the selected member's effective permissions.

This directory is read-only for all current roles: invitation sending, role changes and member removal are unavailable. Platform users.manage does not authorize organization member management. Structural read-only members see identifiers instead of protected names and descriptions. Organization switching clears previous directory selections. The legacy /organizations page remains available with its existing organization-discovery and switching controls.

Workbench Notifications — Action Center: open /workbench/notifications to browse the recent notifications returned for the active organization. Use the unread filter or the notification types supplied by the service, search message/type/reference text, and select an item to inspect its actual message, type, timestamp and optional related record. Mark-read actions remain subject to the existing organization mutation capability. Opening a share notice follows the existing shared-endpoints route. Counts apply only to the loaded recent list. Preference controls and unsupported actor/source/severity fields or workflow actions are not fabricated.

After logging in you'll see three areas:

  • Sidebar (left) — the main menu. Items shown depend on your permissions: Dashboard, Teams, Users, Systems, Environments, Endpoints, Swagger Sync, Auth Profiles, Embedded Test, Governance.
  • Header (top) — contains the notification bell, theme toggle (light/dark), and language switcher (English/Arabic).
  • Main area — where the selected page appears.

On mobile, the sidebar collapses into a hamburger menu, and floating buttons give quick access to theme and language.

5.Dashboard

The Dashboard is your at-a-glance overview. It shows:

  • Totals: number of teams, systems, environments, and endpoints.
  • Unique endpoints: distinct path + method combinations per system.
  • Change counts: how many endpoints are New, Modified, or Deleted since the last sync.
  • Broken Swagger URLs: environments whose Swagger document couldn't be fetched — a quick health signal.
  • Endpoints by Environment: expandable groups (System → Environment) with counts.
  • Recent Syncs: the latest 10 sync runs with status (Success / Failed / Partial), timestamp, and any error messages.

Use it to spot problems (broken URLs, failed syncs) and to see what changed recently.

6.Teams

Teams are the top of the hierarchy. Menu → Teams.

View: a table of teams showing name, description, contact email, Slack channel, number of systems, and created date.

Create a team:

  1. Click Add Team.
  2. Fill in Name, Description, Contact Email, and Slack Channel.
  3. Click Save.

Edit / Delete: use the row actions. Deleting a team is confirmed first.

Creating or editing teams usually requires the teams.manage permission.

7.Systems

A System is one application or service, belonging to a team. Menu → Systems.

Filter: by team, or search by name.

Table shows: system name, description, team, owner (name/email), repository URL, environment count, created date.

Create a system:

  1. Click Add System.
  2. Choose the Team, enter a Name and Description.
  3. Add Owner details and the Repository URL (optional but recommended).
  4. Click Save.

Edit / Delete: row actions. Deleting a system also removes its environments and endpoints — you'll be warned first.

8.Environments

Environments are deployments of a system (Dev, Test, Staging, Production…). Menu → Environments.

Filter: by system, by environment type, by status (Active/Inactive), or search by name. Environments are grouped by system.

Create an environment:

  1. Click Add Environment.
  2. Select the System and enter a Name (e.g. "Development").
  3. Choose the Type: Local, Development, Test, Staging, or Production.
  4. Enter the Base URL — where live requests are sent (e.g. https://api-dev.example.com).
  5. Optionally enter the Swagger URL — the OpenAPI/Swagger JSON document to import endpoints from.
  6. Set Active on, then Save.

Single URL vs. Multi-Source:

  • Single URL — one Swagger document for the environment (the simple case).
  • Multi-Source — multiple Swagger Sources (e.g. one per API version). Switch to the multi-source tab to add several labeled sources, each with its own Swagger URL and base URL.

Per-environment actions: view the last sync status, trigger a manual sync, edit, or delete.

9.Swagger Sync (Importing APIs)

Swagger Sync is what fills the portal with endpoints — automatically. Menu → Swagger Sync (requires swaggersync.view).

9.1 What a Sync Does

  1. Fetches the Swagger/OpenAPI document from each environment's Swagger URL.
  2. Reads every path, method, parameter, header, request body, and response.
  3. Compares against what's already stored and marks each endpoint as New, Modified, Deleted, or Unchanged.
  4. Saves a change history snapshot so you can see exactly what changed.
  5. Records a sync log (status + counts) and notifies users in real time.

9.2 Running a Sync Manually

  • On the Swagger Sync page, find the environment and click its Sync button (a spinner shows while it runs).
  • Or trigger syncs for individual environments from the Environments page.

9.3 Scheduling Automatic Syncs

To keep endpoints fresh without manual effort (requires swaggersync.manageschedule):

  1. Open the Schedule section on the Swagger Sync page.
  2. Pick a Quick Preset (Every hour, Every 6 hours, Daily at 2 AM, …) or build a custom frequency (hourly / every N hours / daily / weekly / monthly with a time or day).
  3. Turn the schedule toggle on.
  4. Click Save. The portal now syncs on that schedule in the background.

9.4 Reading Sync Results

Each environment shows its last status (Success / Failed / Partial), the sync date, and counts of new/modified/deleted endpoints. Failed syncs show an error message (a common cause is an unreachable or invalid Swagger URL).

10.Endpoints — Browse, View, Run

The Endpoints area is the heart of the portal. Menu → Endpoints.

10.1 Browsing & Filtering

Filter the endpoint list by:

  • System, Environment, and Swagger Source
  • HTTP Method (GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS)
  • Tag
  • Change Status (New, Modified, Deleted, Unchanged)

Display options:

  • Grouped view — System → Environment → Tag (expandable tree).
  • Favorites only, Shared with me only, and New sharing only toggles.
  • Multi-select mode — tick checkboxes to share several endpoints at once.

Each row shows a color-coded method badge, the path, summary, tag, change status, last-synced date, a favorite star, a share indicator, and a copy path button.

10.2 Endpoint Detail

Click any endpoint to open its detail page, with tabs for:

  • Parameters — query, path, header, and cookie parameters (name, required, schema, example).
  • Headers — accepted headers and defaults.
  • Request Body — content type + schema with a formatted JSON example.
  • Responses — every status code with its schema.
  • Notes — free-text notes plus a "Used in Pages" field so you can document where the endpoint is used. Editable if you have endpoints.manage.
  • Default Auth Profile — choose which credentials this endpoint uses when tested.

10.3 Running an Endpoint (Live Test)

From an endpoint, open Run (requires endpoints.run):

  1. Optionally override the Base URL.
  2. Pick an Auth Profile (or None).
  3. Fill in Route Parameters and Query Parameters (pre-filled from the schema's examples).
  4. Add or edit Custom Headers (key/value rows).
  5. For POST/PUT/PATCH, edit the Request Body (a skeleton is generated for you).
  6. (Optional) Turn on Mock Mode to return a chosen status code and body without calling the real service.
  7. Click Execute.

The Response panel shows the status code (color-coded), response time in ms, response headers, and a formatted JSON body you can copy. Real requests are saved to the endpoint's request history.

10.4 Change History

Open History on an endpoint to see a timeline of changes (New / Modified / Deleted) with timestamps and a diff viewer (side-by-side, previous, or new snapshot; raw JSON toggle available).

10.5 Generate Client Code

Open Code on an endpoint to auto-generate TypeScript interfaces and an Angular service method for it. Copy each block with one click.

10.6 Export Documentation

You can export endpoint documentation (e.g. to PDF) filtered by system, environment, and tag — handy for sharing with people who don't use the portal (requires export.view).

11.Auth Profiles (Credentials)

Auth Profiles store the credentials used to call endpoints, encrypted at rest. Menu → Auth Profiles (view needs authprofiles.view, editing needs authprofiles.manage).

Supported types:

Type Use it when…
No Auth The endpoint needs no credentials.
Bearer Token You have a token to send in the Authorization header.
API Key The API expects a key in a custom header (e.g. X-API-Key).
Basic Auth You have a username + password.
Custom Header Any single custom header/value.
Auto Login Token The token must be fetched by logging in first (see below).

Create a profile:

  1. Click Add, give it a Name and Description.
  2. Scope it to a System and/or Environment.
  3. Choose the Type and fill the type-specific fields.
  4. Optionally add extra headers, choose a pre-auth profile (to chain logins), and set it as default.
  5. Save.

Auto Login Token (for APIs that require logging in to get a token): provide the login URL, method, a request-body template, the JSON path to the token in the response (e.g. data.accessToken), an optional prefix (e.g. Bearer), and an expiry in seconds. The portal fetches the token automatically and refreshes it when it's about to expire.

Test a profile: click Test to validate the credentials. For auto-login, it performs the login and shows the extracted token, generated headers, response status, and timing — with a button to copy the token.

12.Favorites & Sharing

  • Favorite an endpoint by clicking its star. Filter to Favorites only to find them fast.
  • Share endpoints with teammates: enter multi-select mode, pick endpoints, open the Share panel, and choose to share with a specific user, your team, or multiple teams. You can also share all your favorites at once.
  • Recipients see the endpoints under Shared with me, flagged New until they mark them seen, and get a real-time notification.

13.Embedded Test (Quick Tester)

A lightweight tool for testing any HTTP URL without setting up systems/environments. Menu → Embedded Test.

Manual request:

  1. Choose a method (GET/POST/PUT/PATCH/DELETE).
  2. Enter a URL (must start with http/https).
  3. Paste an Auth Token.
  4. For methods with a body, enter JSON (validated as you type).
  5. Click Send and view the status, timing, headers, and body.

Get Token panel: fetch a token by calling a login endpoint — pick an auth profile or enter a URL/body, specify the JSON path to the token, choose whether to prefix it (e.g. Bearer), then Fetch Token and copy the result.

Saved tests: save the current request under a name; later load, rename, or delete it. Saved tests are private to you.

14.Governance (API Standards)

Governance lets you define standards your APIs should follow and measure compliance. Menu → Governance (Beta; requires governance.view).

14.1 Standards

The Workbench presentation is available at /workbench/governance, using the same standards and authorization as the legacy /governance route. Select a standard in the resource explorer, inspect its policies in the compact rule table, and select a rule to read its configuration. The Assigned resources tab shows existing scope assignments; Validation results and the evidence panel link to recorded reports. Opening these views does not run validation. Active/inactive describes configuration, not compliance.

Standard, rule and assignment changes require governance.manage; running validation requires governance.run and a mutation-eligible organization membership. Structural read-only members see resource identifiers instead of protected policy text and configuration. Workbench forms use side drawers; the legacy presentation remains available.

Create a Standard (e.g. "REST Best Practices") with a name, description, and active toggle. The list shows rule and assignment counts per standard.

14.2 Rules

Inside a standard, add Rules. Each rule has:

  • Type: Regex, Required Field, Response Schema, HTTP Method, Status Code, Custom Expression, or Pagination.
  • Target: what it checks — Path, Method, Summary, Description, Tag, Operation ID, Response Schema, Status Code, Parameters, Security, or Headers.
  • Severity: Info, Warning, Error, or Critical.
  • Expression: the pattern/config, plus an optional error message and suggested fix.

Example rules: "every endpoint must have a tag", "list endpoints must support pagination", "responses must include a success field".

14.3 Assignments

Assign a standard to a scope: a Team, System, Environment, or Swagger Source. Assignments cascade down the hierarchy, so a standard on a system covers all its environments and endpoints.

14.4 Running a Validation

  1. Go to Validate, pick a standard.
  2. Choose a scope (All, Team, System, Environment, or a single Endpoint).
  3. Click Run.

You get an overall compliance score (green ≥80%, yellow ≥50%, red <50%) with passed/failed counts.

14.5 Compliance Report

Open the run's report to see a severity breakdown and per-endpoint results. Expand any endpoint to view each violation: the rule, severity, message, suggested fix, and pass/fail/skip status. Filter by severity or search by path.

15.Notifications

The bell in the header shows your unread count and a dropdown of recent notifications. You'll be notified in real time when:

  • Someone shares endpoints with you.
  • A sync you care about completes.
  • A governance validation finishes.

Click a notification to mark it read, or use Mark all read. Toast pop-ups appear briefly for new events.

16.Users & Roles (Admin)

Administrators manage accounts under Menu → Users (requires users.manage).

Filter: search by username/email/full name, or filter by role or team.

Create a user: provide username, email, a password (6+ characters), full name, a role, and (for Developers) an optional team.

Edit: change a user's role and team. Delete: removes the account (confirmed first).

17.Your Profile & Password

Menu → Profile (or your avatar).

  • Profile: update your username and full name (email, role, and team are read-only). Shows last login and created date.
  • Change Password: enter your current password, then a new password (6+ characters) twice. Click Change Password.

18.Language & Theme

  • Language: switch between English and Arabic from the header. Arabic switches the whole layout to right-to-left (RTL).
  • Theme: toggle light/dark mode from the header. Your choice is remembered.

19.Common Workflows (Recipes)

A. Onboard a brand-new API
Teams → add team → Systems → add system → Environments → add environment with Swagger URL → Swagger Sync → run sync → Endpoints appear.

B. Test an endpoint end-to-end
Auth Profiles → create a profile → Endpoints → open endpoint → Run → pick the profile, fill params/body → Execute → read the response.

C. Keep documentation current automatically
Swagger Sync → Schedule → pick a preset (e.g. Daily at 2 AM) → enable → Save.

D. Share endpoints with your team
Endpoints → multi-select → tick endpoints → Share panel → choose recipients → Share. They get a notification.

E. Check an API against your standards
Governance → create standard → add rules → assign to a system → Validate → run → open the compliance report.

F. See what changed after a release
Endpoints → filter Change Status = Modified/New → open an endpoint → History → view the diff.

21.Troubleshooting & FAQ

I don't see the Users / Swagger Sync / Governance menu.
Those require specific permissions (users.manage, swaggersync.view, governance.view). Ask an admin to grant them.

A sync failed / an endpoint didn't import.
Check the environment's Swagger URL is correct and reachable. The Swagger Sync page and Dashboard show the error message. "Broken Swagger URLs" on the Dashboard highlights these.

My test request returns 401/403.
Your Auth Profile may be missing or its token expired. Open Auth Profiles, Test the profile, and update credentials. For token-based APIs, use an Auto Login Token profile so tokens refresh automatically.

I can't create a team/system/environment.
You need the corresponding *.manage permission.

Where did an endpoint go?
If it was removed from the source API, a sync marks it Deleted. Filter Change Status = Deleted to find it, and check its History.

Someone shared endpoints — where are they?
Endpoints page → toggle Shared with me (they're badged New until seen).

Can I test a random URL without setting up a system?
Yes — use Embedded Test.

22.Glossary

  • Endpoint — a single API operation (method + path), e.g. POST /api/orders.
  • Swagger / OpenAPI — a standard document that describes an API; the portal imports endpoints from it.
  • Swagger Source — one such document; an environment can have several (e.g. per version).
  • Sync — the process of importing/refreshing endpoints from Swagger.
  • Auth Profile — saved, encrypted credentials used to call endpoints.
  • Auto Login Token — an auth profile that logs in to fetch and refresh a token automatically.
  • Change Status — whether an endpoint is New, Modified, Deleted, or Unchanged since the last sync.
  • Governance / Standard / Rule — definitions of how APIs should behave, and checks that measure compliance.
  • Compliance Score — the percentage of checks an API passes.
  • Team / System / Environment — the organizational hierarchy the portal is built around.
